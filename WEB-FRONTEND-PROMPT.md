# Web frontend prompt — azure-resource-downloader documentation browser

<!-- For Claude Code. Scaffold and run inside a `web/` subdirectory of the repo (see §0). Iteration 1 of a documentation web frontend. -->

Build a **NestJS** web application that browses the Markdown documentation generated by
`azure-resource-downloader` (see `DOC-GENERATION-PROMPT.md` in this repo for how that documentation is
produced and structured).

**Iteration 1 has one job: render the existing Markdown files as HTML.** No search, no auth, no editing,
no database, no API for third parties. Resist scope creep — every feature below that is not listed is out
of scope. Note anything you think is missing in a `NEXT-ITERATIONS.md` rather than building it.

---

## 0. Where this lives

This repository root is a **Go module** — an Azure resource downloader. Do **not** scaffold the Node app at
the root: a root-level `package.json`, `node_modules/` and Nest sources would clutter the Go project and
confuse its tooling. Create the app in a **`web/` subdirectory** and keep everything (sources,
`package.json`, build output, `NEXT-ITERATIONS.md`) inside it.

- Package manager: **npm**. Node: **>= 20** (NestJS 11 requires it; the dev machine runs Node 22).
- `DOCS_ROOT` defaults to the repo's export folder — `../output` relative to `web/` — and is overridable via
  the `DOCS_ROOT` environment variable. All commands (`npm run start:dev`) run from inside `web/`.

## 1. What it renders

The app serves documentation from **tenant folders**. A tenant folder is any directory under the
configured docs root that contains **both**:

- `index.md`
- `.doc-manifest.json`

Both must be present. A folder with only one of them is not a tenant and is skipped — this is what
distinguishes a finished export from a half-written or unrelated directory.

Discovery is a scan of the docs root (default `./output`, overridable via the `DOCS_ROOT` environment
variable), non-recursive beyond finding those marker files — walk at most 3 levels deep so a stray deep
tree can't stall startup.

**Stop descending once a folder matches.** A tenant folder contains its own subtree (`<provider>/…`) and
housekeeping directories such as `_to_delete/` — none of those are tenants. As soon as a directory has both
marker files, record it as a tenant and do **not** recurse into it looking for more. This prevents a nested
`index.md`/manifest pair (e.g. under `_to_delete/`) from being surfaced as a phantom second tenant. Skip any
directory whose name starts with `_` or `.` outright.

Inside a tenant folder the documents live at `<provider>/<resourceType>/<name>.md`, e.g.
`Microsoft.Graph/conditionalAccessPolicies/ca01_highprivsignins.md`. Each has YAML frontmatter:

```yaml
---
source: ca01_highprivsignins.yaml
sourceSha256: 9f2b…
promptSha256: 4ad1…
generatedAt: 2026-08-13T08:26:34Z
---
```

`index.md` has **no** frontmatter and is fully derived — treat it as an ordinary page.

## 2. Routes

| Route | Renders |
|---|---|
| `GET /` | Tenant picker — every discovered tenant folder, with its resource count and the manifest's `generatedAt` |
| `GET /:tenant` | That tenant's `index.md`, rendered |
| `GET /:tenant/*path` | The document at `<tenant>/<path>.md`, rendered |
| `GET /healthz` | `{ status, tenants, documents }` — useful for checking discovery worked |

**The resource count is computed, not stored.** `.doc-manifest.json` has no count field — sum the entries
across `types[*].resources` (186 in the reference tenant). Note this is the count of *documented, in-scope*
resources: the generator deliberately excludes bulk directory types (`groups` except referenced ones,
`windowsAutopilotDeviceIdentities` — see `DOC-GENERATION-PROMPT.md` §1), so it will **not** equal the raw
`.md` file count on disk. `documents` in `/healthz` is the same computed sum across all tenants.

**Route wildcard syntax is framework-version-sensitive.** Pin the Express major explicitly and match the
syntax to it: on Express 5 / `path-to-regexp` v8 (the NestJS 11 default) a bare `*` is invalid — the named
form `*path` used above is correct, and the segments arrive as an array to be joined with `/`. If you pin
Express 4 instead, use its `*` wildcard. Do not mix the two.

Links inside `index.md` are relative (`Microsoft.Graph/<type>/<file>.md`), and links *inside documents* are
relative with `..` (e.g. an assignment table links `../groups/<file>.md`). Rewrite `.md` hrefs at render
time so they resolve to app routes: strip the `.md` suffix and resolve relative to the current page. A link
to an anchor within the same page (`#some-heading`) must be left untouched.

**Rendered-link `..` is not the same surface as request-path `..`.** The `..` inside a markdown href is
legitimate and, once the browser resolves it against the current URL, produces a clean request path with no
`..` in it (`../groups/x` from a policy page becomes `Microsoft.Graph/groups/x`). The traversal rejection in
§5 applies to the **incoming request path param**, not to hrefs you emit — do not strip or reject `..` while
rewriting links, or every cross-type link breaks.

Unknown tenant or document → a 404 page that says which tenant and path were requested, and links back to
the picker. Never leak an absolute filesystem path into an error page.

## 3. Markdown rendering

### Use `markdown-it`

**`markdown-it@15`** is the right choice here, and the reason is specific to these documents rather than a
general preference:

- **These docs are full of raw HTML.** Every property in every generated page is a `<details>`/`<summary>`
  disclosure block — thousands of them across a tenant. `markdown-it` with `html: true` passes raw HTML
  through, and its CommonMark-correct HTML-block handling is what makes Markdown *inside* a `<details>`
  block still render as Markdown (an HTML block ends at a blank line, so the content after it is parsed
  normally). This is exactly how these files already render on GitHub and in VS Code — VS Code's preview
  *is* `markdown-it` — so what you see in the editor is what the site will show.
- **Clean, class-free semantic HTML.** `markdown-it` emits plain `<h2>`, `<table>`, `<details>` with no
  injected classes and no inline styles, so all styling is external CSS. That is what makes it easy to
  restyle.
- **The plugins this needs already exist and are maintained**: `markdown-it-anchor@9` for heading IDs,
  `markdown-it-attrs@5` if you later need to attach classes from Markdown, `@shikijs/markdown-it@4` for
  syntax highlighting.

Considered and rejected: **`marked`** is faster but has a thinner plugin ecosystem for anchors and
attributes; **`remark`/unified** is the most powerful (full mdast→hast AST access) but brings a
multi-stage pipeline whose value shows up in Next.js/Astro/MDX projects — it is overhead here.

### Configuration

```ts
import MarkdownIt from 'markdown-it'
import anchor from 'markdown-it-anchor'

const md = new MarkdownIt({
  html: true,        // REQUIRED — the <details> blocks are the documentation
  linkify: true,
  typographer: false, // keep it off: it mangles quotes and dashes inside config values
})
md.use(anchor, { permalink: anchor.permalink.headerLink(), tabIndex: false })
```

- `html: true` is **not optional**. Without it every property block renders as escaped text and the pages
  are worthless.
- **Do not run the output through an HTML sanitizer that strips `<details>`, `<summary>` or table markup.**
  The input is generated by this repo from the tenant's own export — it is not user-submitted content.
  If you add sanitization anyway (e.g. `sanitize-html`), you must allowlist `details`, `summary`, `table`,
  `thead`, `tbody`, `tr`, `th`, `td`, `code`, `pre`, `em`, `strong`, `a`, `br`.
- Parse frontmatter with **`gray-matter@4`**. Strip it from the rendered body and surface it as page
  metadata (source YAML filename, `generatedAt`). Never render the raw `---` block as content.
- Syntax highlighting is **optional in iteration 1**. If you add it, use `@shikijs/markdown-it`; the code
  fences in these docs are `yaml`, `bash`, `powershell`, `json` and `xml`.

### Rendering strategy — render on request, cache by mtime

Render lazily and cache:

1. On request, `stat()` the `.md` file.
2. If the cache holds an entry for that path with the same `mtimeMs` and size, serve the cached HTML.
3. Otherwise read, render, store `{ html, mtimeMs, size, frontmatter, title }`, serve.

A regenerated document appears on the next request with **no restart**. That matters because the
documentation prompt is still being iterated on — the loop is regenerate, refresh, look.

Cache the tenant discovery result too, but with a short TTL (~30 s) so a newly generated tenant folder
appears without a restart. Bound the page cache (an LRU of ~500 entries is ample; a large tenant is ~160
documents at ~15 KB of HTML each).

## 4. Styling — Tailwind CSS v4 + typography plugin

Use **`tailwindcss@4`** with **`@tailwindcss/typography@0.5`**. Wrap rendered Markdown in
`<article class="prose prose-slate dark:prose-invert max-w-none">`.

Tailwind v4 is **CSS-first** — there is no `tailwind.config.js` by default. Configure in the stylesheet:

```css
@import "tailwindcss";
@plugin "@tailwindcss/typography";

@theme {
  --color-brand-500: oklch(0.55 0.15 250);
}
```

Build the stylesheet as a normal build step and serve the compiled CSS from Nest's static assets
(`ServeStaticModule` or `app.useStaticAssets`). Do not pull Tailwind from a CDN.

Concretely, compile with the Tailwind v4 CLI (`@tailwindcss/cli`) from your input stylesheet to a static
file the app serves, and wire it into `package.json` so `npm run start:dev` also rebuilds CSS on change:

```jsonc
"scripts": {
  "css:build": "tailwindcss -i ./src/styles.css -o ./public/app.css --minify",
  "css:watch": "tailwindcss -i ./src/styles.css -o ./public/app.css --watch",
  "start:dev": "npm run css:build && concurrently \"npm:css:watch\" \"nest start --watch\""
}
```

Serve `./public` statically and link `/app.css` from the page shell. Add `public/app.css` to `.gitignore` —
it is build output.

### The one thing typography does not solve

`@tailwindcss/typography` styles standard prose elements. It has **no styles for `<details>` and
`<summary>`**, and those are the dominant visual element in these documents — a page can be 200 of them.
Untouched, they render as bare, unindented disclosure triangles and the pages look broken.

Write explicit CSS for them, in the same stylesheet, scoped under `.prose`:

- `summary` — clear affordance that it is clickable: pointer cursor, medium weight, a hover background,
  and a visible `:focus-visible` ring for keyboard users.
- `details` — a left border or subtle surface fill, and padding so nested blocks read as nested. **These
  nest several levels deep** (a settings-catalog policy has group settings containing child settings), so
  verify indentation still reads correctly at depth 3.
- `details[open] > summary` — a distinct state so an open block is obvious when several are expanded.
- `summary > code` — property paths appear inside summaries and should not inherit prose's inline-code
  background twice.

Also worth handling: these documents contain **wide tables** (assignment tables with long GUIDs). Give
`.prose table` a horizontal scroll container rather than letting it overflow the page.

Dark mode via `prefers-color-scheme` and `dark:prose-invert`. Check the `<details>` styling in both — a
border colour that reads well on white often vanishes on dark.

## 5. Structure

Standard Nest layout. Suggested shape, adapt if you have a better one:

- `DocsModule` — the feature module.
- `TenantDiscoveryService` — scans `DOCS_ROOT`, finds folders with both marker files, reads
  `.doc-manifest.json` for counts and `generatedAt`, caches with a short TTL.
- `MarkdownRendererService` — owns the `markdown-it` instance and the mtime-keyed cache. One instance,
  configured once at construction, not per request.
- `DocsController` — the four routes.
- Templating: a minimal view engine (Handlebars or EJS via `@nestjs/platform-express`) for the page shell —
  `<head>`, stylesheet link, header with tenant name and breadcrumb, and a slot for the rendered HTML.
  The Markdown-derived HTML is inserted **unescaped** (`{{{ body }}}` in Handlebars) — that is intentional
  and is the whole point; escaping it produces a page of visible tags.

### Path safety

`GET /:tenant/*path` takes a filesystem path from a URL. Before reading:

- Reject any path containing `..`, a null byte, or a leading `/`.
- Resolve the candidate to an absolute path and verify with a prefix check that it is still inside that
  tenant's folder — after `realpath`, so a symlink cannot escape.
- Only serve files ending in `.md`.

Write a test for the traversal case (`/tenant/../../etc/passwd`) — it is the one security-relevant surface
in an app this small.

## 6. Acceptance criteria

The iteration is done when:

1. `npm run start:dev` with the repo's real `output/` directory discovers `cb-gmbh.com` and lists it on `/`
   with its resource count.
2. `/cb-gmbh.com` renders `index.md`, including the collapsible platform groups, and its links navigate to
   real document pages.
3. A settings-catalog document — e.g.
   `/cb-gmbh.com/Microsoft.Graph/deviceManagementConfigurationPolicies/gbl_cp_prd_d_cis_win_firewall_l1` —
   renders its `<details>` blocks as working, visibly styled disclosure widgets, nested correctly, with
   the tables readable.
4. Editing a `.md` file on disk and refreshing shows the change without a restart.
5. A folder under `output/` missing `.doc-manifest.json` is **not** listed as a tenant.
6. Path traversal is rejected, with a test proving it.
7. Light and dark both look deliberate.

### Verify by looking

Do not declare it done from unit tests alone. Start the app and take screenshots of the index page and of
one settings-catalog document in both colour schemes, and check the `<details>` blocks actually look like
disclosure widgets at nesting depth 3. The failure mode here is a page that is technically correct and
visually unreadable.
